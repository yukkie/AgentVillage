## 優先度の価値観

- リファクタリング vs 新機能: 新機能優先（実装漏れ中心）
- tech-debt の姿勢: 後回し（ゲーム完成を優先）
- バグ修正: 重篤度・影響範囲による（軽微なものは後回し可）
- 安定性 vs 速度: バランス（MVPを最短距離で）
- 設計原則: YAGNI / KISS / DRY を基本としつつ SOLID を意識する
- 拡張性: 見えている将来の拡張（例: GUI対応）に対して閉じた設計はNG。
  ただし「あるかもしれない拡張」は対象外（YAGNIとの両立）
- エージェントの思考品質: 動くだけでなく「なぜその行動をしたか」が追跡可能であることを重視。
  reasoning / belief / memory の連鎖が観戦体験の核になる。

## 優先度の判断基準

### 工数 vs 優先度
- **低工数 (SP 1–2) の tech-debt は即着手する**。後回しにするコスト（認知負荷の蓄積）が
  工数を上回るため、他 Issue の優先度に関わらず high 扱いにする。
- 工数が大きい (SP 5+) tech-debt は他 Issue との依存・影響範囲を考慮して medium 以下で調整する。

### 依存関係 vs 優先度
- **他 Issue の前提となる Issue（ブロッカー）は、自身の工数・種別に関わらず優先度を上げる**。
  例: SP1 でも他の medium Issue を unlock するなら high にする。

### 構造改善 vs 新機能
- **新機能の実装が不要になる構造改善は、新機能より優先する**。
  「新機能優先・tech-debt は後回し」の例外。
  実装漏れ機能を新規実装するより、設計改善で同じ要件を吸収できるならその方が
  コードベースのシンプルさが保たれ、長期的な保守コストも下がる。
  例: tool use 化により Day 2+ CO 判断フェーズが OPENING に吸収できる場合、
  tool use 化を先に行う。

### テスタビリティ vs 優先度
- **テストが書けない / 書きにくい設計・実装（モジュールレベルシングルトン、隠れた副作用など）は
  工数・種別に関わらず high 扱いにする**。
  テストなしの実装は検証不可能になるため、放置コストが大きい。

### エラーハンドリング vs 優先度
- **ゲームが止まる / リプレイが壊れる**実害のあるエラー処理抜けは **medium**。
- **サイレントに伝播するが通常は発生しない**エラー処理抜けは **low**。
  放置しても負債が蓄積しないため、他の tech-debt より後回しでよい。

### UT必須の原則
- **実運用での再現が難しいパス（エラーハンドリング・エッジケース・レアケース）には、
  優先度に関わらず単体テストを必ずセットで実装する**。
  テストなしの修正は検証不可能になるため、Issue 本文に `⚠️unit test mandatory` を明記する。
